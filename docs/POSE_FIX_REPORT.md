# Проверка распознавания и подсчёта FitCounter

## Окружение

Проект собирается с minSdk 19, compileSdk и targetSdk 37. На физическом планшете ADB подтвердил Project Tango Tablet Development Kit, Android 4.4.2, API 19 и ARMv7. Пользовательская сборка принимает NV21 через Android Camera API. MoveNet SinglePose Lightning INT8 v4 получает RGB 192×192 и выдаёт 17 наборов из координат и confidence. В комплект входит TensorFlow Lite 2.16.1 с двумя потоками CPU. Сборки нативной библиотеки предназначены для ARMv7 и x86. Резервный профиль PoseNet MobileNetV1 использует вход 257×257, карты вероятностей и смещения суставов. [Описание MoveNet](https://www.tensorflow.org/hub/tutorials/movenet), [совместимость проекта](COMPATIBILITY_REPORT.md).

## Причины и изменения

| Симптом | Причина в исходной реализации | Изменение |
| --- | --- | --- |
| Скелет на мебели и предметах | Модель находит ключевые точки даже на кадрах без человека. Слой отрисовки принимал отдельные точки по confidence. | Проверка торса, связанных сегментов, пропорций, координат и согласованности между двумя кадрами. При неподтверждённой позе нет ни скелета, ни угла. |
| Потеря суставов в движении | На полном кадре человек занимал малую часть входа 192×192, особенно в нижней фазе. В записи приседаний выпадали колено и лодыжка, в отжиманиях confidence локтя и запястья опускался к границе фильтра. | После подтверждения человека модель получает область вокруг тела с полями для движения. При потере позы поиск возвращается к полному кадру. Углы рассчитываются по текущей геометрии до сглаживания отображения. |
| Пропущенные повторения | Исходный счётчик выбирал сторону на весь подход. Пропуск сустава сбрасывал текущую фазу. | Левая и правая стороны независимо подтверждают движение вниз, глубину, подъём и верх. При зачёте сбрасывается потенциальный дубль от второй стороны. Настройки углов действуют для обеих сторон. Амплитуда таза или плеча дополнительно подтверждает глубину. |
| Мигание предупреждения | Статус зависел от результата одного кадра. | Предупреждение об отсутствии человека или нужных суставов выдерживает 650 мс. Для восстановления требуются два пригодных кадра. Для запаздывающих результатов предусмотрен отдельный статус. Короткий пропуск сохраняет счёт подхода и позволяет продолжить подтверждённую фазу при наличии промежуточного измерения. |
| Скелет отставал от видео | Полный кадр стабильно пересчитывался с ограничением 120 мс между запусками. UI получал отдельную задачу на каждый результат, а предпросмотр продолжал показывать более свежий кадр. | Один кадр в обработке и одна заменяемая позиция для следующего кадра и результата. Идентификаторы кадров защищают порядок публикации. Пары изображения и скелета строятся из одного NV21 и используют общий поворот и зеркальность. Положение быстро движущихся точек сглаживается слабее. Просроченная пара убирается через 350 мс. |
| Иконка переключения камеры | Кнопка рисовала собственный контур. | Векторный ресурс с контуром камеры и круговыми стрелками. Сборка генерирует PNG по плотностям для API 19. В приложении переключается передняя или задняя камера. |

Подтверждение глубины и верха требует измерений. Если после нижней фазы человек впервые появляется уже в верхней точке, цикл приходится начать заново. Если пропущены только начальные кадры в верхнем положении, измеренная верхняя точка позволяет сохранить готовность к следующему циклу. Так сохраняются завершённые повторения и исключается зачёт по одному восстановленному кадру.

## Воспроизведение

Видеодекодирование выполняет FFmpeg на компьютере. Инструментальный тест читает кадры NV21 с относительными временными метками и передаёт их модели, валидатору и счётчику из штатного APK. Разметка содержит окна завершения повторений и интервалы ожидаемой потери измерений. Отчёт проверяет попадание каждого события в отдельное окно. Во время последовательного видеопрогона обрабатываются все кадры из выборки с частотой 8 кадр/с по времени записи. Этот режим измеряет качество на воспроизводимой последовательности. Частоту обработки live-потока измеряет отдельный тест камеры.

```powershell
.\gradlew.bat :app:assembleDebug :app:assembleDebugAndroidTest :app:testDebugUnitTest :app:lintDebug
$adb = "$env:LOCALAPPDATA/Android/Sdk/platform-tools/adb.exe"
& $adb install -r app/build/outputs/apk/debug/app-debug.apk
& $adb install -r app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
python tools/fetch-pose-fixtures.py
python tools/test-pose-media.py tools/pose-fixtures.json --media-dir build/pose-media --adb $adb
& $adb shell am instrument -w -e class com.example.fitcounter.ExampleInstrumentedTest com.example.fitcounter.test/androidx.test.runner.AndroidJUnitRunner
```

Для нескольких устройств укажите нужный серийный номер через `adb -s` и `--serial`. Скрипты требуют Python 3 и FFmpeg. Если FFmpeg отсутствует в PATH, укажите путь через `--ffmpeg`. Повторный запуск отдельного сценария доступен через `--fixture`. Временные кадры остаются на локальных носителях на время теста. Сводка и покадровые JSONL по умолчанию сохраняются в `build/pose-media/results`.

## Результаты на Android 4.4.2 x86

Последовательный прогон обработал 503 кадра на AVD API 19 через MoveNet из APK. Все зарегистрированные повторения попали в свои размеченные окна. [JSON со сводкой](pose-media-results-api19.json).

| Сценарий | Эталон → результат | Подтверждённые позы | Предупреждения |
| --- | ---: | ---: | ---: |
| Приседания | 5 → 5 | 124/125 | 0 |
| Отжимания | 5 → 5 | 110/111 | 0 |
| Приседания, ускорение 1,45× | 5 → 5 | 85/86 | 0 |
| Отжимания, выход за границу кадра и перекрытие руки | 5 → 5 | 108/111 | 0 |
| Движущиеся фигуры, пустая комната, мебель и плитка | 0 → 0 | 0/50 | По одному переходу в «Человек в кадре не обнаружен» на сценарий |
| Фото отжимания и стоп-кадр приседания | 0 → 0 | 18/20 | 0 |

В двух интервалах перекрытия отсутствовало пригодное измерение угла на трёх кадрах и на одном кадре соответственно. За это время счёт не менялся. До уточнения восстановления прогон на AVD пропускал первое отжимание и давал 4 из 5. Теперь повторение подтверждено после восстановления исходной позы, наблюдения нижней фазы и возвращения вверх.

Сборка основного и инструментального APK, 14 модульных тестов, lint без ошибок. Java-код резервного профиля PoseNet прошёл компиляцию. Финальные тесты на устройстве с Android проводились с MoveNet. На AVD прошли тесты чтения фото моделью, потока Camera → MoveNet, повторного открытия камеры, переключения между двумя камерами и через кнопку активного подхода, отрисовки повёрнутого и зеркального изображения, очереди кадров, переходов в календарь и статистику и сохранения SQLite. Отдельный инструментальный тест подтвердил программную отрисовку пар из изображения и позы. Замена камеры сбрасывает незавершённую фазу, а активный подход остаётся открытым.

## Производительность и проверка Tango

Сравнение двух запусков теста Camera → MoveNet на одном AVD API 19, 60 измерений на сборку. Время указано в мс как p50/p95.

| Метрика | Исходная сборка | Финальная сборка |
| --- | ---: | ---: |
| Обработка, кадр/с | 2,75 | 2,79 |
| От callback камеры до результата | 369/408 | 366,8/390,5 |
| Выполнение модели | 348/396 | 351,1/375,5 |

На финальном потоке 640×480 эмулятор подавал около 42,6 callback/с. Очередь занимала 13,4/22,0 мс, подготовка входа 0,9/3,6 мс, постобработка 0,047/0,556 мс. В отдельном тесте 80 последовательно поступивших кадров последний результат доставлен, все 80 буферов освобождены, число доставленных результатов оказалось меньше десяти. Это подтверждает сброс устаревших кадров при перегрузке.

На открытом экране тренировки AVD обновлял TextureView примерно 21,3 раза/с. Два замера PSS приложения при работающем предпросмотре дали 16,5 и 16,2 МиБ. Длительную нагрузку с подтверждённой позой на физическом устройстве ещё предстоит проверить.

На быстром видео подтверждённые позы обрабатывались за 314,6/380,0 мс внутри модели. Подготовка входа занимала 1,24/1,60 мс, постобработка 0,065/0,095 мс, сглаживание 0,017/0,020 мс, расчёт углов 0,018/0,020 мс. На отдельном тесте 30 кадров с человеком программная копия изображения заняла 3,6/9,6 мс, рисование пары в Canvas 2,2/2,8 мс, полный путь от поступления буфера до окончания рисования 324,7/371,3 мс. Это измерение Canvas на AVD. Задержка сенсора и физического дисплея в него не входит.

На исходной сборке физический Tango обработал 7,95 кадр/с. Время от callback камеры до результата составило 134/205 мс, вывод модели 86/124 мс. Планшет пропал из ADB после первого видеопрогона. Финальные измерения на ARMv7, включая вывод на экран, тест живых подходов и проверку длительной работы, остаются открытыми. Камера API 19 отмечает время прихода буфера в callback, поэтому задержка экспозиции и доставки из HAL требует отдельного внешнего измерения. Цель до 150 мс для финальной сборки на Tango остаётся неподтверждённой.

Текущая проверка покрытия ограничена четырьмя отрицательными сценариями и двумя исходными видеозаписями. MoveNet SinglePose отслеживает одного человека. Стабильность при разных ракурсах, освещении и смене человека в кадре требует отдельного набора.
